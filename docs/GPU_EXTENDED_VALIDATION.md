## 已证实的因果链

1. column 5 是季节融雪 clay 情景，残余薄雪在失败前一步只有
   `SWE=0.001287519803081481 m`，本步压实后密度 306.373284538 kg/m³，厚度
   0.004202454548288317 m，旧雪温为 273.15 K。
2. `driver.step_column` 用旧雪温求雪面能量平衡，得到
   `Ts=267.52075562399233 K`、`G=−133.9752146124391 W/m²`，本步残差仅
   `−7.5163e-6 W/m²`。随后把这个 G 当作整个1800秒固定顶边界，送进
   `snow.apply_snow_heat`。
3. 仅一层雪、底部绝热时，所谓隐式层间求解没有可耦合的内部界面，温度更新
   恰好简化为 `T_new = T_old + dt·G/(C_SNOW·depth)`。此例单位面积热容为
   `630000×depth = 2647.546365421640 J/(m² K)`，故
   `ΔT = −91.086369421895 K`，结果 **182.0636305781052 K**。
   该更新没有隐式反馈雪温变化对表面 G 的影响。
4. 下一步气温仍为262.991166158 K；把已经过冷的雪温放入同一表面能量函数，
   `[200,330] K` 的131个扫描点 F 全为负，范围
   `[−7288.956747966, −245.453656676] W/m²`。没有扫描到符号括区间，求解器
   按既有逻辑返回最佳点200 K。不是求解器忘记迭代，也不是 float32 精度地板。
5. 对**同一冻结状态的 F** 将诊断搜索区间延至 `[100,200]`，在
   `190.36375685364624 K` 找到连续根，残差 `3.6948e-13 W/m²`。
   这只帮助定位根跑出允许区间，不能把放低200 K保护界作为合理物理修复。

初始土壤/水量范围正常，前三日最大累计水量余额约3.92e-16 m。
问题来自薄雪小热容量承受旧状态计算的固定通量后过冷，随后状态进入求根区间
无法闭合的范围。只有“热求解器采用隐式 Thomas”不足以保证这种分裂式表面边界
更新在长时间步下稳定。

## 下一步与修复候选

在 xuanze GPU0 以相同输入、相同每日 carry 顺序发起 JAX x64/x32 的7日预检，
两者前2日通过、第3日触发相同能量门后停止；7日未完成、365日未执行。
手写CUDA年度测试也未执行。年度保持红灯，没有把失败后重置初态的重复调用
算作全年连续积分。

物理修复应另建明确的普通版/JAX/CUDA一致性变更：

- 优先评估把表面 G 对新雪温的反馈写入雪层隐式边界，使表面温度求解与雪层
  温度更新耦合；同一候选 Ts 内更新雪温并定义一致的界面通量，避免旧态 G
  被整步固定。该方案会改变普通版数值轨迹，不能在后台基准仍运行时悄悄修改。
- 另一候选是对表面能量与薄雪热更新共同自适应子步；子步需覆盖整个耦合链并
  守恒，不能仅把现有固定 G 多分几段（固定 G 的累计温降完全相同）。
- 不采用简单温度 clipping、减小残差报告值、降低Ts保护下界或删掉薄雪情景来
  获得绿灯；这些都不能修复本次证明的通量/热容量失配。

一个可审查的局部修复起点是**单层、不融化、冻结导热系数**的分析切片。
令单位面积热容为 C、表面导热系数为 K，隐式边界联立
`C(Tn+1−Tn)/dt = G = K(Ts−Tn+1)` 可消去新雪温，得到
`G = [KC/(C+dt·K)]·(Ts−Tn)`。把这个一致的 G 放入地表 F(Ts)，再用同一 G
更新雪温，可以避免本次按旧温度固定通量的过冲；C、K>0 时新温度是旧雪温和
Ts 的加权平均。这只是单层无相变情景的推导，尚不是可直接上线的通用补丁。
多层雪需要把 Thomas 系统对顶边通量的响应并入边界；进入融化还需与焓/潜热
转换共同处理。必须验证水量、能量和旧方案对照后，再同步三个后端。

当前 probe 只诊断、返回原求解器根，不改物理。复现命令：

```bash
PYTHONPATH=src python benchmarks/probe_annual_failure.py \
  --input docs/gpu-results/j4-annual-numpy-smoke.jsonl \
  --output outputs/j4-annual-failure-root-probe-new.json
```

在任一修复候选落地后，需要重跑同一失败窗口、连续7日，再进行365日；普通版
与 GPU 同时更新并重新验证 H2/H4，旧基准因源代码变化须单独标识。

### x32同精度阻塞：batch shape影响单步诊断

同样的column2输入，N=64800与N=1均为实际CUDA float32，在零基step17出现
3个诊断超差，其他步未超差，最终完整fvec精确相同。比较门为
`abs(actual−expected) <= 1e-6 + 1e-6*abs(expected)`，没有放宽。

| 字段 | N=64800 | N=1 | 绝对差 | 超过容差倍数 |
|---|---:|---:|---:|---:|
| H W/m² | 7.376016616821289 | 7.376476764678955 | 4.60147858e-4 | 54.9333 |
| G W/m² | 132.45773315429688 | 132.4582061767578 | 4.73022461e-4 | 3.54435 |
| residual W/m² | 0.0004425048828125 | -0.0006256103515625 | 1.068115234e-3 | 1067.4474 |

这是同精度、同输入、不同batch shape的计算差异，不能归为float64对照的精度
预算。shape改变XLA lowering或运算顺序是待定位候选，当前证据还不能把具体
FMA/迭代路径定为根因。最终状态相同也不能抵销已保存的逐步诊断超差。应在
单独的最小复现中比较该步输入与HLO/融合运算，修复前保持此项红灯。

此外，x32对NumPy采用`rtol=1e-4, atol=1e-6`的原样严格门，15个样本都至少在
residual失败，一些还涉及近零H/G/rnet/melt。两列的块末有效状态ABI8
（ice[0]）也超差：col6为0.021111920476对0.021107905934，差4.01454e-6；
col55542为0.024162687361对0.024158332989，差4.35437e-6。它们不是无效雪层
填充值问题。当前没有应用待用户确认的残差分档容差；即使只调整residual也
不能自动使这些状态与其他诊断项通过。
