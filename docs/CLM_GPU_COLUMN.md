# 开发中的 CLM 无雪整柱 GPU 入口

`gpu.clm_column.step_clm_columns_jax` 和
`gpu.cuda.clm_column.step_clm_columns_cuda` 对应 NumPy
`clm_driver.step_clm_column`，不是旧 big-leaf 驱动的 GPU 别名。
准备冠层边界、Farquhar/Ball–Berry/叶温空气联立、土壤水热更新均在设备执行。
Python 包装层负责输入与收敛检查，不调用 NumPy 物理来生成 GPU 状态。

入口暂用 v0.2.0 的 70 浮点 / 33 整数向量，固定四土层厚度
`[0.1, 0.3, 0.6, 1.0] m`、十冠层。`pack_clm_columns` 会拒绝其他土层厚度，
避免序列化后悄悄丢失几何。五层雪和 BGC 状态扩展将另行更新布局。
已有雪或降雪明确报未实现；只有已有雪槽位、没有冬季解算不算支持雪。

## 设备上的一步

1. 刷新液水/冰、截留降雨，计算液态水胁迫、阻力和共享根区/地表供水上限。
2. 调用已经独立核验的三后端冠层联立器；未收敛时不提交土壤更新结果。
3. 把冠层联立给出的每层根吸水原量扣入土壤，计入凝露、滴落、入渗与排水，
   然后推进土温。根系与地表蒸发不能各自消耗同一份表层液水。
4. 返回新向量与 `CLM_DIAGNOSTICS` 指定的 22 个诊断。可用
   `return_canopy=True` 取得逐层温度、通量和气体交换的完整诊断。

`site_array` 的五列依次为 CO₂、太阳天顶角余弦、散射比例、叶尺度和氮容量
因子；可按柱输入。默认值是显式假设，尚未完成真实测高/太阳几何映射。
目前上方 MOST 用旧地温，叶边界层摩擦速度仍为中性估计，与 NumPy 开发柱
一致；这也是默认生产路径尚未切换的原因之一。

## 已定位的初次失败

随机工况第一次有12个柱诊断同精度超门，最大6.103516e-5 W/m²，主要在近零
预算残差。准备阶段的HLO显示摩擦速度之后的两次除法被合并，且新调用位置
的地表阻力常数折叠与旧全柱图不同。给摩擦速度和水量/潜热中间量增加局部
舍入屏障，CUDA在新入口匹配其常数运算顺序；未改旧土壤Thomas或放宽门。
失败报告和HLO保存为 `p2-column-before-rounding.json.gz` 和
`p2-column-prepare-hlo.txt.gz`。最终88柱和连续轨迹已复验。

首次七天运行完成后，报告脚本错误地把`h_wm2`当作带层号变量，导致统计失败；
日志 `p2-column-report-script-error.log.gz` 保留。已修复，并在汇总前保存原始
轨迹；上面的最终数字来自完整重跑，不是把脚本崩溃当作成功。

Windows共享Conda出现过访问异常及pytest导入阶段SystemError，按
[环境阻塞](GPU_BLOCKERS.md)绕行Linux。没有把GPU跳过算通过。wheel已构建并
确认包含五个CUDA源文件，发布版本仍为0.2.0，未提前合并或创建v1.0.0标签。
